# Make it better

งานจบเมื่อถึงเงื่อนไขหยุดในขั้น 3 ทุกรอบที่เก็บไว้ชนะรอบก่อนในสายตา judge ที่ไม่รู้ว่าอันไหนใหม่ และ flow หลักยังทำงานครบ

สั่ง "make it better" ซ้ำแบบไม่มีทิศทาง งานจะกลายเป็นการ **เพิ่มของ**: ในการทดลอง 100 รอบ Opus ทำเว็บร้านกาแฟโตถึง 21,000 บรรทัด ฟีเจอร์พังเอง และไม่ค้นเว็บหา reference เลยสักครั้ง skill นี้แก้ด้วย vision ก่อนลงมือ, reference จากของจริง, รอบละหนึ่งการเปลี่ยน, เก็บเฉพาะที่ชนะ และหยุดเมื่อไม่ดีขึ้นแล้ว

## กติกาตลอดงาน

- **ที่เก็บงาน**: target ต้องอยู่ใน git ถ้ายังไม่อยู่ให้ `git init` แล้ว commit สภาพเดิม สร้าง branch `make-it-better/<ชื่อ>-<YYYYMMDD>` เอกสารของงานอยู่ใน `.make-it-better/` ที่ root (เพิ่มลง `.git/info/exclude`): `VISION.md`, `rounds.md`, `shots/`
- **รอบละหนึ่งการเปลี่ยน** ที่อธิบายได้ในประโยคเดียว รอบที่เก็บไว้เป็นหนึ่ง commit `round N: <ประโยคนั้น>`
- **ไม่ต้องเปลี่ยนทุกรอบ**: ถ้าไม่มีข้อเสนอที่คาดว่าชนะ ให้จด "ไม่มีข้อเสนอที่คุ้ม" แล้วนับเป็นรอบที่ไม่ผ่าน
- **ขนาดคือต้นทุน**: จดจำนวนบรรทัดของโค้ด (หรือจำนวนคำของเอกสาร) ทุกรอบ ถ้า judge ตัดสินเสมอ ให้เก็บฉบับที่เล็กกว่า ทุกรอบที่ 5, 10, 15, ... เป็น **รอบตัด**: เลือกได้เฉพาะข้อเสนอที่ลบ รวม หรือทำให้ง่ายลง
- **flow หลักต้องผ่านทุกรอบ**: รอบที่ทำให้ flow หลักพังถือว่าแพ้ ไม่ว่าจะสวยขึ้นแค่ไหน
- **งาน UI**: อ่าน `~/.claude/agent-skills/ux-ui.md` ก่อนเริ่ม ทดสอบใน ego-browser ทั้ง desktop และ mobile ถ้ามี shadcn MCP ให้ค้น component ใน registry ก่อนเขียนเอง
- **งบ**: รอบสูงสุดค่าเริ่มต้นคือ 10 รอบละราว USD 2-6 ถ้ารอบสูงสุดคูณค่าต่อรอบเกินราว USD 30 ให้ถามก่อน
- ไม่ push และไม่ deploy จนกว่าผู้ใช้จะสั่ง

## 1. Vision และ scorecard

1. ดูของจริงก่อน: เปิด target (เว็บใน ego-browser ถ่าย screenshot เต็มหน้าทั้ง desktop และ mobile เก็บใน `shots/round-0-*`) แล้วจดว่ามีอะไรบ้าง
2. เขียน `VISION.md`:
   - **ผู้ใช้**: เป็นใคร และมาเพื่อทำอะไร (งานหลัก 1-3 อย่าง)
   - **ความรู้สึก**: 3 คำที่ผู้ใช้ควรรู้สึก
   - **นอกขอบเขต**: สิ่งที่ห้ามเพิ่มหรือห้ามแตะ
   - **flow หลัก**: flow ที่ต้องไม่พัง พร้อมคำสั่งหรือ ego-browser script ที่ตรวจได้
   - **scorecard**: 4-6 เกณฑ์ คะแนน 1-5 ทุกเกณฑ์มีตัวอย่างว่า 1, 3 และ 5 หน้าตาเป็นแบบไหน ต้องมีเกณฑ์ **โฟกัส** (ผู้ใช้ทำงานหลักได้เร็วโดยไม่มีของเกินมาเกะกะ) เสมอ งานเว็บเพิ่มตัววัดที่วัดได้: console error เป็น 0 และ Lighthouse performance กับ accessibility
   - **เป้า**: ค่าเริ่มต้นคือทุกเกณฑ์ได้ 4 ขึ้นไป
3. ถามผู้ใช้รอบเดียว (AskUserQuestion ไม่เกิน 4 ข้อ ตัวเลือกที่แนะนำไว้แรก) เฉพาะข้อที่อ่านจาก argument หรือ target ไม่ได้ เช่น ผู้ใช้เป้าหมาย, สไตล์, ส่วนที่ห้ามแตะ, จำนวนรอบ ข้อที่เลือกเองให้ใส่ `(สมมติ)`

เสร็จเมื่อ: ทุกเกณฑ์ใน scorecard มีตัวอย่างครบสามระดับ และคำสั่งตรวจ flow หลักผ่านบนสภาพเดิม

## 2. Reference และ backlog

1. ค้นเองด้วย WebSearch (`mode: "standard"`) ตาม `VISION.md` ทีละมุม ส่งคำค้นของทุกมุมพร้อมกันใน message เดียว:
   - **ตัวอย่างที่ดีที่สุดในประเภทเดียวกัน**: คู่แข่งที่เก่งที่สุด และงานที่ได้รางวัล (งานเว็บ: Awwwards, Godly, Land-book)
   - **pattern ที่พิสูจน์แล้ว**: งานวิจัย UX, คู่มือ conversion หรือแนวทางของงานประเภทนี้
   - **ของสำเร็จรูป**: component หรือ template ที่ใช้ได้ (shadcn registry, 21st.dev)
   
   แต่ละมุมได้ข้อเสนอ 3-5 ข้อ: สิ่งที่ reference ทำได้ดีแต่ target ยังไม่มีหรือทำได้แย่กว่า พร้อม URL ที่มา
2. ตรวจ reference ที่ดีที่สุด 2-3 ตัวเองใน ego-browser แล้วถ่าย screenshot เก็บไว้
3. เขียน **backlog** ใน `VISION.md`: ข้อเสนอ / ที่มา / เกณฑ์ที่น่าจะดีขึ้น / ขนาดโดยประมาณ ใส่ข้อเสนอที่ลบหรือทำให้ง่ายลงด้วย
4. ให้ judge (ดูขั้น 3 ข้อ 4) ให้คะแนนสภาพเดิมตาม scorecard แล้วจดเป็นรอบ 0 ใน `rounds.md`

เสร็จเมื่อ: backlog มีอย่างน้อย 8 ข้อ ทุกข้อมีที่มา และรอบ 0 มีคะแนน

## 3. วนรอบ

ทำซ้ำจนถึงเงื่อนไขหยุด:

1. **เลือก**: หยิบ 3 ข้อจาก backlog รวมกับข้อเสนอใหม่จากสิ่งที่เห็นในรอบก่อน ให้คะแนนแต่ละข้อว่าคาดว่าได้คะแนนเพิ่มเท่าไรต่อขนาดที่เพิ่ม แล้วเลือกข้อเดียว ถ้าเป็นรอบตัด เลือกได้เฉพาะข้อที่ลบหรือทำให้ง่ายลง ถ้าไม่มีข้อไหนคุ้ม ให้ข้ามไปข้อ 6
2. **ทำ**: แก้เฉพาะสิ่งที่เลือก
3. **ตรวจ**: รันคำสั่งตรวจ flow หลัก, test และ typecheck ที่เกี่ยวข้อง, ดู console และ network error, ดูจอ mobile ถ้าพังให้แก้ได้ 1 ครั้ง ถ้ายังพังให้ revert
4. **judge**: ส่ง subagent ใหม่ที่ไม่มีบริบทของงานนี้ ให้ได้แค่ scorecard จาก `VISION.md` กับผลงานสองฉบับที่ตั้งชื่อเป็น X และ Y (งานเว็บใช้ screenshot เต็มหน้าทั้ง desktop และ mobile) สลับว่าฉบับใหม่เป็น X หรือ Y ในแต่ละรอบ ให้คะแนนทุกเกณฑ์ของทั้งสองฉบับ แล้วเลือก X, Y หรือเสมอ พร้อมเหตุผล
5. **ตัดสิน**: เก็บเมื่อ judge เลือกฉบับใหม่, ไม่มีเกณฑ์ไหนลดลงเกิน 1 และตัววัดที่วัดได้ไม่แย่ลง ถ้าเสมอให้เก็บฉบับที่เล็กกว่า ฉบับที่เก็บให้ commit ส่วนฉบับที่ไม่เก็บให้ย้อนกลับไป commit ล่าสุดที่เก็บไว้ แล้วจดเหตุผลไว้ข้างข้อนั้นใน backlog เพื่อไม่เสนอซ้ำ
6. **จด**: เพิ่มแถวใน `rounds.md`:

   | รอบ | การเปลี่ยน | ผล (เก็บ / ย้อน / ไม่มีข้อเสนอ) | คะแนนรวม | ขนาด | เหตุผลของ judge |
   |---|---|---|---|---|---|

**หยุดเมื่อ**: ไม่ได้เก็บติดกัน 3 รอบ, ทุกเกณฑ์ถึงเป้า หรือครบรอบสูงสุด

## 4. ตรวจรอบสุดท้ายและรายงาน

1. ส่ง judge ใหม่ 2 ตัวเทียบสภาพเดิมกับฉบับสุดท้ายแบบซ่อนชื่อ ถ้าทั้งคู่ไม่เลือกฉบับสุดท้าย ให้รายงานตามนั้นตรงๆ
2. รัน flow หลัก test และ typecheck ชุดเต็มหนึ่งครั้ง
3. รายงานในแชท:
   - คะแนนรอบ 0 เทียบกับรอบสุดท้ายทุกเกณฑ์ ขนาดก่อนและหลัง และผลของ judge 2 ตัว
   - ตารางจาก `rounds.md`
   - screenshot ก่อนและหลังคู่กัน (ส่งด้วย SendUserFile)
   - เหตุผลที่หยุด และข้อเสนอใน backlog ที่ยังไม่ได้ลอง
   - ชื่อ branch แล้วเสนอ `mrn:ship` ถ้าจะเอาขึ้นจริง
