# Eval

งานจบเมื่อมีคำตัดสินที่ตอบเกณฑ์ของผู้ใช้ได้ พร้อมหลักฐานที่รันซ้ำได้ และรายงาน PDF คำตัดสินมีได้ 4 แบบ: **ดีกว่า**, **ไม่ต่าง**, **แย่กว่า** หรือ **สรุปไม่ได้ (inconclusive)** ต้องบอก N ทุกครั้ง

## กติกาตลอดงาน

- **ที่เก็บงาน**: ทุกอย่าง (case, script, raw output, รายงาน) อยู่ใน `<cwd>/evals/<ชื่อ eval>-<YYYYMMDD>/` ถ้า cwd เป็น `$HOME` หรืออยู่ใต้ `/tmp`, `/private/tmp` หรือ scratchpad ให้ใช้ `~/evals/` แทน raw output ทุกครั้งที่รันต้องบันทึกลงไฟล์ทันที ตารางในรายงานต้องมาจากไฟล์เหล่านี้
- **เทียบให้ยุติธรรม**: ทุกฝั่ง (arm) ใช้ input ชุดเดียวกัน, เครื่องเดียวกัน, งบเวลาเท่ากัน และวิธีให้คะแนนเดียวกัน ถ้าทำไม่ได้ ให้เขียนในรายงานว่าเอนเอียงไปทางไหน
- **งบ**: ประเมินค่าใช้จ่ายก่อนรัน (agent หนึ่งรอบราว USD 1-7) ถ้ารวมเกินราว USD 20 หรือนานเกินราว 30 นาที ให้ถามผู้ใช้ก่อนด้วย AskUserQuestion พร้อมเสนอแบบเล็กกว่า
- **ของจริงที่ปลอดภัย**: ห้ามจ่ายเงิน, ส่งข้อความถึงคนจริง หรือแตะ production ถ้าต้อง login ให้ผู้ใช้ login เองใน ego-browser
- **ขนาน**: arm และ case ที่ไม่ใช้ทรัพยากรร่วมกันให้รันพร้อมกัน แต่ benchmark ความเร็วต้องรันทีละตัว เพราะรันพร้อมกันจะแย่ง CPU กัน

## 1. ตั้งโจทย์

เขียน `PLAN.md` สั้นๆ ในโฟลเดอร์ eval:
- **เป้าหมาย**: สิ่งที่ถูก eval คืออะไร และอยู่ที่ไหน (path, ชื่อ plugin, URL)
- **เกณฑ์**: ใช้ตามที่ผู้ใช้สั่ง ถ้าไม่ได้สั่ง ให้ดึงจากสิ่งที่เป้าหมายอ้างว่าทำได้ (description ของ skill, README, หน้าขายของ) แล้วเขียนเป็นข้อที่วัดได้ เช่น "ผ่าน hidden check", "เวลา", "ค่าใช้จ่าย", "คะแนน rubric" และกำหนดว่าต่างแค่ไหนถึงนับว่าต่าง
- **คู่เทียบ**: ตามข้อ 2
- **วิธี, จำนวน case, จำนวนรอบ และงบ**: ตามข้อ 3

ถามผู้ใช้เฉพาะเมื่อการตีความแต่ละแบบให้ eval คนละเรื่องกันเลย นอกนั้นให้เลือกเองแล้วเขียนเป็นสมมติฐานใน `PLAN.md`

## 2. คู่เทียบ

ผู้ใช้ระบุมา: ใช้ตามนั้น แล้วเพิ่ม baseline ข้อ (b) ด้วยถ้าทำได้ถูก

ไม่ได้ระบุ: หาเองตามลำดับนี้ แล้วเลือก 1-2 ตัวที่ใกล้เคียงที่สุด พร้อมเขียนเหตุผลที่เลือก
- **(a) เวอร์ชันก่อน**: `git log` / `git show HEAD:<file>` หรือ version เก่าใน `~/.claude/plugins/cache/<marketplace>/<plugin>/`
- **(b) baseline ที่ไม่มีสิ่งนั้น**: agent ที่ไม่มี skill หรือ plugin นี้, prompt ที่ไม่มีกฎนี้ หรือโค้ดเส้นทางเดิม
- **(c) ทางเลือกในเครื่อง**: `claude plugin list`, รายชื่อ skill ใน session, CLI ที่ติดตั้งอยู่ (`which`, `brew list`, `npm ls -g`)
- **(d) ทางเลือกจากเว็บ**: WebSearch (`mode: "standard"` ก่อน) หาเครื่องมือหรือผลิตภัณฑ์คู่แข่งในหมวดเดียวกัน แล้วเลือกตัวที่คนใช้จริงและเทียบได้ในเครื่องนี้ ตัวที่ต้องติดตั้งเพิ่มให้ใช้ไฟล์ชั่วคราว (`npx`, `uvx`, venv ในโฟลเดอร์ eval) ห้ามติดตั้งแบบ global โดยไม่ถาม

ถ้าหาคู่เทียบไม่ได้เลย ให้ใช้ baseline (b) อย่างเดียว และบอกในรายงานว่าเทียบกับตัวเองตอนไม่มีสิ่งนั้น

## 3. เลือกวิธีตามประเภทเป้าหมาย

| เป้าหมาย | วิธี |
|---|---|
| skill หรือ plugin | `claude plugin eval` เป็นตัวแรก (ดู `claude plugin eval --help`): เขียน case ใน `evals/` ของ plugin (prompt.md + graders) แล้วใช้ `--ablation with-without` ได้ arm ไม่มี plugin มาเองฟรี ถ้าจะเทียบกับ plugin อื่น ให้รัน suite เดียวกันกับแต่ละ target ถ้าใช้ไม่ได้ ให้ทำ A/B ด้วย `claude -p` ตาม [ab-eval.md ของ prove-it](../prove-it/ab-eval.md) |
| prompt, CLAUDE.md, hook หรือ config ของ agent | A/B ด้วย `claude -p` ตาม [ab-eval.md](../prove-it/ab-eval.md): hidden check, แยก config ด้วย flag, probe ก่อนรันจริง |
| โค้ด, function, CLI หรือความเร็ว | benchmark: input เดียวกันหลายขนาด (เล็ก, ปกติ, ใหญ่, edge case) ใช้ `hyperfine` ถ้ามี (`--warmup 2 --runs 10 --export-json`) ไม่มีก็วนรันเองอย่างน้อย 10 รอบต่อ arm แล้วรายงาน median และ p95 ต้องเช็คก่อนว่า output ของทุก arm ถูกต้องตรงกัน ตัวที่เร็วแต่ผิดถือว่าแพ้ |
| คุณภาพของผลงาน (รายงาน, เอกสาร, คำตอบ, design) | ให้ judge agent อย่างน้อย 2 ตัวให้คะแนนตาม rubric ที่เขียนไว้ก่อน โดยซ่อนชื่อ arm (ตั้งเป็น X/Y) และสลับลำดับ แต่ละข้อใน rubric ต้องมีตัวอย่างว่าแบบไหนได้กี่คะแนน และถ้า judge 2 ตัวให้คะแนนต่างกันเกิน 1 ระดับ ให้ตัวที่ 3 ตัดสิน |
| เว็บ, UI หรือผลิตภัณฑ์ | เดินงานหลักเดียวกันทุก arm ใน ego-browser แล้ววัดจำนวนขั้นตอน, จำนวนคลิก, เวลา, error และ Lighthouse (performance, accessibility) พร้อมถ่าย screenshot คู่กัน |

**ชุด case**: 3-8 case แต่ละ case วัดคนละเกณฑ์ และต้องมี:
- **guard** อย่างน้อย 1 ข้อ: case ที่ต้องได้ผลไม่แย่ลง
- **hard** อย่างน้อย 1 ข้อ: case ที่ยากหรือเป็น edge case

grader หรือ hidden check ต้องอยู่นอกที่ที่ agent มองเห็น และต้องรันกับผลที่ผิดให้ได้ fail ก่อน 1 ครั้ง เพื่อพิสูจน์ว่า check จับผลผิดได้จริง

**จำนวนรอบ**: งานที่ใช้ agent อย่างน้อย 2 รอบต่อ case ต่อ arm (ผลแต่ละรอบไม่เหมือนกัน) ส่วน benchmark ตามแถวในตาราง

## 4. รัน

1. **probe**: รัน 1 รอบต่อ arm ก่อน เพื่อยืนยันว่าแต่ละ arm ได้ config หรือ input ที่ตั้งใจจริง ถ้าผิดให้แก้ก่อนรันจริง
2. **รันจริง**: arm ที่ไม่แย่งทรัพยากรกันให้รันขนาน (`xargs -P` หรือ background) บันทึก raw output ต่อรอบ
3. **วัด**: ผล check, เวลา, ค่าใช้จ่าย (`total_cost_usd` จาก event `result` ของ stream-json) และพฤติกรรมที่เกณฑ์ถาม

## 5. วิเคราะห์

- อ่าน run ทุกตัวที่ผลต่างจากที่คาด อย่าดูแค่ค่าเฉลี่ย
- ตัดสินทีละเกณฑ์ งานที่ใช้ agent ให้รายงาน pass^k (ผ่านครบทุกรอบหรือไม่) แทนค่าเฉลี่ย
- ต่างกันน้อยกว่าความผันผวนระหว่างรอบ หรือ N น้อย (เวลาต่างไม่เกินราว 30% เมื่อ N=2) ให้ตัดสินว่า **สรุปไม่ได้** และบอกว่าต้องรันเพิ่มแค่ไหนถึงจะสรุปได้
- ถ้าเจอว่า eval เองผิด (check จับผลผิดไม่ได้, arm ได้ input ไม่เท่ากัน) ให้แก้แล้วรันส่วนนั้นใหม่ และเขียนไว้ในรายงาน

## 6. รายงาน PDF

เขียน `REPORT.md` ในโฟลเดอร์ eval เป็นภาษาไทย:

1. **หัวเรื่อง** (`#` บรรทัดแรก) แล้วตามด้วยย่อหน้าแรกที่ตอบคำตัดสินพร้อม N
2. **ตารางสรุปต่อเกณฑ์**: เกณฑ์ / arm แต่ละตัว / ผลต่าง / คำตัดสิน
3. **ตารางต่อ case**: ผลของทุก arm ทุกรอบ
4. **คู่เทียบ**: ใช้อะไร ได้มาจากไหน และทำไมถึงเลือก
5. **วิธีที่ใช้** และคำสั่งที่รันซ้ำได้
6. **ข้อจำกัด**: ส่วนที่ไม่ยุติธรรม, ส่วนที่วัดไม่ได้ และ N ที่ควรมีถ้าจะสรุปให้แน่น
7. screenshot (ถ้ามี) ให้ฝังด้วย path เต็ม `![...](/abs/path.png)`

แปลงเป็น PDF: `bash "{path_to_skill}/scripts/md-to-pdf.sh" "<โฟลเดอร์ eval>/REPORT.md"` (`{path_to_skill}` คือ directory ที่ SKILL.md นี้ถูกโหลดมา) script จะพิมพ์ path ของ PDF ออกมา ให้ `open` PDF และบอก path ของทั้ง .md และ .pdf ถ้า script fail ให้ส่งแค่ .md พร้อมเหตุผล

คำตอบในแชท: คำตัดสินหนึ่งประโยค, ตารางสรุปต่อเกณฑ์, ข้อจำกัดสำคัญ และ path ของ PDF
