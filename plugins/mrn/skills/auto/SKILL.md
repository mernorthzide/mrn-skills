# Auto

อ่านงานของผู้ใช้ เลือก skill ที่เหมาะที่สุด บอกผู้ใช้หนึ่งบรรทัดว่าเลือกตัวไหนและเพราะอะไร แล้วเรียกใช้ทันที ไม่ต้องถามก่อน ยกเว้นกรณีในข้อ "ถามเมื่อไหร่"

## ตารางเลือก

ดูจาก **ผลลัพธ์ที่ผู้ใช้อยากได้** ไม่ใช่คำที่ใช้ แล้วเลือกแถวแรกที่ตรง:

| ผู้ใช้อยากได้ | skill | สัญญาณ |
|---|---|---|
| merge worktree หรือ branch นี้ขึ้น main แล้วเก็บกวาด | `mrn:finish-worktree` | "จบ worktree", "เอาขึ้น main", "merge แล้วลบ worktree" |
| เว็บใหม่ที่ลอกจากเว็บต้นแบบ | `mrn:copy-it` | มี URL ของเว็บคนอื่น + "ทำเหมือน", "ลอก", "clone" |
| demo หรือต้นแบบเว็บที่กดได้จริงจากไอเดีย ไว้นำเสนอลูกค้า | `mrn:prototype` | "prototype", "ทำ demo ให้ลูกค้า", "ต้นแบบ", "POC", "mockup ที่กดได้" (ไม่มีเว็บต้นแบบให้ลอก) |
| พิสูจน์ว่าการแก้ใช้ได้จริง หรือแก้ bug ที่รู้แล้วพร้อมหลักฐาน | `mrn:prove-it` | "พิสูจน์", "prove", "แก้ bug นี้", "fix", diff ที่แตะเงิน, security, data, concurrency หรือ contract |
| รายการ bug ของระบบหรือ feature ที่ยังไม่รู้ว่าพังตรงไหน | `mrn:qa` | "ทดสอบ", "เทส", "หา bug", "QA", "ตรวจก่อนขึ้น production" (หา ไม่ใช่แก้) |
| คำตัดสินว่า A ดีกว่า B ไหม โดยวัดจากการรันจริง | `mrn:eval` | "eval", "benchmark", "เทียบว่าดีกว่าไหม", "วัดผล", A/B ของ skill, prompt หรือ config |
| รายงานที่สรุปจากหลายแหล่งข้อมูล (ไม่ได้รันอะไรเอง) | `mrn:deep-research` | "research", "หาข้อมูล", "เปรียบเทียบตลาด", "วิเคราะห์เทรนด์", "ราคา ณ ตอนนี้" |
| แผนปรับโครงสร้างโค้ด, module ที่ควรทำให้ลึกขึ้น | `mrn:improve-codebase-architecture` | "สถาปัตยกรรม", "refactor ภาพรวม", "โค้ดยุ่ง", "testability" |
| งานใหญ่ที่แบ่งได้หลายชิ้นอิสระ ให้เสร็จเร็วที่สุด | `mrn:swarm` | หลาย module, หลายไฟล์ หลายหน้า หรือหลาย item ที่ไม่ขึ้นกัน, "ให้เร็วที่สุด", "แตก agent" |

**แยกตัวที่คล้ายกัน**
- `qa` ใช้หา bug ที่ยังไม่รู้ ส่วน `prove-it` ใช้แก้หรือพิสูจน์สิ่งที่รู้แล้ว ถ้าผู้ใช้บอกอาการ bug มาแล้ว ให้ใช้ `prove-it`
- `eval` ได้ตัวเลขจากการรันจริงในเครื่อง ส่วน `deep-research` ได้ข้อมูลจากแหล่งอ้างอิง ถ้า "เทียบ X กับ Y" แล้วรันในเครื่องได้ ให้ใช้ `eval` ถ้าเป็นบริการ ราคา หรือตลาด ให้ใช้ `deep-research`
- `swarm` คือวิธีทำงาน ไม่ใช่ประเภทของงาน ใช้เมื่องานสร้างหรือแก้ของมีหลายชิ้นอิสระจริง ถ้างานตรงกับแถวอื่นด้วย ให้ใช้แถวนั้น (เช่น `copy-it` และ `prototype` แตก agent เองอยู่แล้ว)
- `copy-it` ใช้เมื่อมีเว็บต้นแบบให้ลอก ส่วน `prototype` ใช้เมื่อเริ่มจากไอเดีย และ `prototype` ทดสอบด้วย `qa` เองอยู่แล้ว ไม่ต้องต่อ `qa` อีก

**ต่อกันหลาย skill**: ถ้างานมีหลายผลลัพธ์ต่อกัน ให้ทำตามลำดับ และบอกลำดับตั้งแต่แรก เช่น:
- "ลอกเว็บนี้แล้วทดสอบให้ด้วย" → `copy-it` → `qa`
- "แก้ bug นี้แล้วเอาขึ้น main" → `prove-it` → `finish-worktree`
- "ทำ feature ทั้งหมดนี้ให้เร็ว แล้วเทสก่อนขึ้น" → `swarm` → `qa`
- "ทดสอบหา bug แล้วแก้ให้หมด" → `qa` → `prove-it` (แก้ทีละ bug ตามความรุนแรง)

**ไม่มีแถวไหนตรง**:
- มี skill อื่นในรายชื่อ skill ของ session ที่ตรงกว่า (เช่น `impeccable` สำหรับงานออกแบบ UI, `mattpocock-skills:diagnosing-bugs` สำหรับ bug ที่ยังไม่รู้สาเหตุ, `mattpocock-skills:tdd`): ใช้ตัวนั้น
- เป็นงานเล็ก (แก้ typo, rename, ตอบคำถาม, commit): ทำเองเลยโดยไม่ใช้ skill และบอกว่าไม่ได้ใช้เพราะอะไร

## ถามเมื่อไหร่

ถามด้วย AskUserQuestion เฉพาะเมื่อตัวเลือกที่เป็นไปได้ 2 ตัวให้ผลต่างกันมาก **และ** ตัวที่เลือกผิดแพง (เช่น `copy-it` ที่ลอกทั้งเว็บ เทียบกับ `qa` ที่ทดสอบเว็บเดียวกัน) นอกนั้นให้เลือกเองแล้วบอกเหตุผลในบรรทัดเดียว

## เรียกใช้

- skill ทั่วไป: เรียก Skill tool ด้วยชื่อเต็ม (`mrn:<ชื่อ>`) และส่งงานของผู้ใช้เป็น `args` ตามที่ผู้ใช้เขียนมา ห้ามย่อหรือตัดเงื่อนไขทิ้ง
- `mrn:improve-codebase-architecture` เรียกผ่าน Skill tool ไม่ได้ (ตั้งให้ผู้ใช้เรียกเองเท่านั้น) แต่ผู้ใช้สั่งผ่าน auto แล้ว จึงให้ Read `{path_to_skill}/../improve-codebase-architecture/SKILL.md` แล้วทำตามทุกขั้น (`{path_to_skill}` คือ directory ที่ SKILL.md นี้ถูกโหลดมา)
- ต่อกันหลาย skill: รอ skill แรกจบจริงก่อน แล้วส่งผลลัพธ์ที่เกี่ยว (path ของรายงาน, รายการ bug, branch) เป็น `args` ให้ skill ถัดไป

## --dry-run

ถ้า args ขึ้นต้นด้วย `--dry-run` ห้ามเรียก skill และห้ามลงมือทำงาน ให้ตอบเป็นบรรทัดเดียวตามรูปแบบนี้ แล้วจบ:

```
AUTO: <skill หรือ skill1 -> skill2 หรือ none> | <เหตุผลสั้นๆ>
```
