# Prove it

งานนี้จบเมื่อทุก **claim** มี **evidence** ที่คนอ่านรันซ้ำได้ หลักฐานที่นับคือ **oracle** ที่ **red** บนโค้ดเดิมด้วยเหตุผลที่ถูก แล้ว **green** บนโค้ดใหม่ โดย oracle ตัวเดิมทุกตัวอักษร

## เลือก tier ก่อน

| tier | งาน | ทำขั้นไหน |
|---|---|---|
| trivial | ข้อความ, config, แก้บรรทัดเดียวที่ไม่แตะ logic | claim 1 ข้อ, oracle 1 ตัว, ขั้น 2 และ 6 |
| normal | bug fix, feature ทั่วไป | ขั้น 1-4 และ 6 |
| risky | diff เปลี่ยนสูตรหรือ logic ของเงิน (ปัดเศษ, ส่วนลด, ภาษี, คืนเงิน, ตัดยอด), security, data/migration, concurrency/cache, contract/API, diff เกินราว 200 บรรทัด | ทุกขั้น รวมขั้น 5 |

โค้ดที่แค่แสดงหรือส่งต่อตัวเลขเงินโดยไม่เปลี่ยนวิธีคำนวณเป็น normal บอก tier ที่เลือกพร้อมเหตุผลหนึ่งบรรทัดตอนเริ่ม

## เครื่องมือ: ใช้ตัวที่มีจริง

แต่ละงานข้างล่างมีหลายทางเลือก ใช้ตัวแรกในลำดับที่มีอยู่จริงใน session นี้ ตรวจจากรายการ tool และ skill ที่โหลดอยู่ หรือ `command -v <ชื่อ>` ก่อนใช้ ถ้า CLAUDE.md หรือกฎของผู้ใช้กำหนดเครื่องมือไว้ ให้ใช้ตามนั้นก่อนตาราง การติดตั้งเครื่องมือใหม่ต้องถามผู้ใช้ก่อน

| งาน | ลำดับทางเลือก |
|---|---|
| **browser** (งาน UI) | browser skill หรือ MCP ที่ผู้ใช้กำหนด → browser automation ใดๆ ที่มี (Playwright, Chrome DevTools, Claude in Chrome) → เรียก HTTP ด้วย `curl` ตรวจ HTML/API แล้วจด claim ด้านหน้าจอไว้ใน "ยังไม่ได้พิสูจน์" |
| **ผู้ตรวจอิสระ** | review tool ภายนอกที่ผู้ใช้ใช้อยู่ (เช่น Codex) → subagent ใหม่ผ่าน Agent tool → ถ้าไม่มีทั้งคู่ ทำรอบตรวจแยกโดยอ่านแค่ diff กับ claim แล้วระบุในรายงานว่าไม่ใช่ผู้ตรวจอิสระ |
| **ความเห็นที่สองเมื่อติด** | เครื่องมือ diagnosis ภายนอกที่ผู้ใช้ใช้ (เช่น Codex) → subagent ใหม่แบบ read-only → ข้ามไปแนวทางถัดไปแล้วบันทึกว่าไม่มีความเห็นที่สอง |
| **blast radius** | code graph ที่ repo มี (เช่น `graphify affected`) → LSP หรือ find references → `rg` / `grep` |
| **baseline** | `git worktree add <ที่เก็บหลักฐาน>/base HEAD` → คัดลอกไฟล์ที่จะแก้ไว้ก่อนแก้ (repo ไม่มี git) → revert check |
| **ที่เก็บหลักฐาน** | scratchpad ของ session → `$TMPDIR/proof/` → ถ้าสิทธิ์ไม่ให้เขียนนอก project: `.proof/` ใน repo โดยเพิ่ม `.proof/` ลง `.git/info/exclude` ก่อนเขียน (repo ไม่มี git: ลบ copy ของโค้ดที่ใช้ทำ baseline/mutation ทิ้งตอนจบ เก็บแค่ไฟล์ output) แล้วบอก path ในรายงาน |
| **test runner** | คำสั่งที่ repo ประกาศไว้ (`package.json` scripts, `Makefile`, `pyproject.toml`) → runner มาตรฐานของภาษา (`node --test`, `python -m unittest`, `go test`) → script assert สั้นๆ ไว้ในที่เก็บหลักฐาน |

ในรายงาน ให้บอกในหนึ่งบรรทัดว่าแต่ละงานใช้ทางเลือกไหน เมื่อไม่ได้ใช้ตัวแรก

## กติกาตลอดงาน

- **test เดิมคือ spec**: ทำให้ผ่านด้วยการแก้โค้ดเท่านั้น โค้ดต้องทำงานถูกกับ input ทั่วไป ไม่ใช่แค่ค่าที่ test ใช้ ถ้า test ผิดหรือขัดกันเอง ให้หยุดแล้วรายงานว่าข้อไหนขัดกับข้อไหน พร้อมเสนอทางเลือกให้ผู้ใช้ตัดสิน การเปลี่ยน assertion, snapshot, หรือ skip/only/xfail ใดๆ ต้องเป็นแถวของตัวเองในรายงานพร้อมเหตุผล
- **raw evidence**: ทุกครั้งที่รัน oracle ให้บันทึกคำสั่งและ output ลง **ที่เก็บหลักฐาน** ทันที (`<claim>-before.txt`, `-after.txt`) ไฟล์เหล่านี้ต้องไม่ติดไปกับ commit ตารางในรายงานต้องมาจากไฟล์เหล่านี้
- **ของจริงที่ปลอดภัย**: เรียก API จริงได้เฉพาะ local, staging หรือ sandbox ห้ามแตะ production, การชำระเงิน, การส่งอีเมล/SMS ถึงคนจริง และ API ที่คิดเงิน ข้อมูลทดสอบที่สร้างขึ้นต้องลบหลังจบ
- ไม่ mock ตัวที่กำลังพิสูจน์ และใช้ DB engine เดียวกับที่ใช้จริง

## 1. เขียน claim

อ่านคำขอของผู้ใช้กับ diff แล้วเขียน claim ทีละข้อ claim คือประโยคที่จริงหรือเท็จได้จากสิ่งที่สังเกตเห็น: "สมัครด้วยชื่อไทยแล้วมี row ใน DB", "คืนเงินเต็มยอดแล้วเหลือ 0 พอดี"

- ที่มาของ claim: สิ่งที่ผู้ใช้ขอ, พฤติกรรมเดิมที่ต้องไม่พัง, และ **blast radius** คือ caller ของโค้ดที่แก้ (หาด้วยเครื่องมือ **blast radius**) ถ้า caller เยอะ ให้ใส่ oracle หนึ่งตัวต่อพฤติกรรมที่ต่างกัน แล้วระบุ caller ที่เหลือว่าใช้แบบเดียวกัน
- แต่ละ claim ผูกกับ oracle หนึ่งตัว: test, คำสั่ง CLI, การเรียก API, query DB, หรือการเดิน flow ใน **browser** พร้อม screenshot
- **ค่า expected มาจาก spec, ตัวอย่างของผู้ใช้, หรือค่าที่คำนวณด้วยมือเป็น literal** ไม่ใช่จากการรันโค้ดที่กำลังพิสูจน์หรือก๊อปสูตรของมันมา
- oracle ตัดสินจากผลปลายทาง (ข้อมูลที่บันทึก, ตัวเลข, หน้าจอ) ไม่ใช่ log ของโค้ดตัวเอง
- claim เรื่องเงินหรือตัวเลขต้องมี oracle จากแถว "เงินและตัวเลข" ใน [edge-matrix.md](edge-matrix.md) อย่างน้อยหนึ่งตัว (เช่น `0.1 * 3`, ยอดมีสตางค์หลายรายการ) ค่าที่เลือกต้องเป็นค่าที่ทำให้โค้ดผิดได้ ไม่ใช่ค่าที่ผ่านง่าย

เสร็จเมื่อ: ทุก claim มี oracle ที่รันได้ และค่า expected ทุกค่ามีที่มานอกโค้ด

## 2. ทำให้ oracle red บน baseline

รัน oracle กับโค้ดก่อนแก้ด้วยเครื่องมือ **baseline** แล้วคัดลอกเฉพาะไฟล์ oracle เข้าไป (ไม่ใช้ `git stash` เพราะไฟล์ใหม่ที่ยังไม่ track จะค้างอยู่และทำให้ baseline ปน)

- claim ที่เป็น bug หรือ feature ใหม่ต้อง red และ **red ต้องเป็น assertion failure ที่ข้อความบอกค่า expected ของ claim นั้น** ถ้าเป็น import error, crash, typo หรือ selector หาไม่เจอ แปลว่า oracle ยังไม่ได้วัด claim ให้แก้แล้วรันใหม่
- ถ้าได้ green แปลว่า oracle วัดไม่ถูกจุด ให้แก้ oracle ก่อนไปต่อ claim ประเภท regression ต้อง green ทั้งสองฝั่ง
- ถ้ารัน baseline ไม่ได้ (ไม่มี git, UI ที่ต้องยก server ชุดเก่า) ให้ใช้ **revert check** หลังแก้เสร็จ: ย้อนบรรทัดสำคัญของการแก้ทีละจุด ดูว่า oracle red แล้วใส่กลับ ถ้าทำไม่ได้ทั้งสองแบบ ให้เขียน `N/A: <เหตุผล>` ในช่องก่อนแก้
- งาน bug fix ที่ยังไม่ได้แก้ ขั้นนี้คือ **reproduce**: เขียน test ที่ red ตามอาการของผู้ใช้ก่อนแตะ src
- จากนี้ไป **ห้ามเปลี่ยน oracle** ถ้าจำเป็นต้องเปลี่ยน ให้รัน baseline ใหม่และแสดง diff ของ oracle ในรายงาน

เสร็จเมื่อ: ทุก claim ที่ต้อง red เห็น assertion red จริงพร้อมไฟล์ raw evidence หรือมี N/A พร้อมเหตุผล

## 3. เดินแบบผู้ใช้ แล้วโจมตี

- เดิน flow หลักผ่าน entry point จริงด้วยข้อมูลหน้าตาเหมือนจริง (ชื่อไทย, ยอดเงินมีสตางค์, ข้อความยาว)
- เลือกแถวจาก [edge-matrix.md](edge-matrix.md) เฉพาะที่ diff แตะจริง แล้วแปลงเป็น oracle
- ดู **side channel**: console, network ที่ fail, log ฝั่ง server, ข้อมูลที่ถูกเขียน error ที่ไม่ได้มีอยู่บน baseline นับเป็น finding
- **flaky**: งาน async, UI หรือ concurrency ให้รัน oracle ที่ green อย่างน้อย 3 รอบ ถ้าผลสลับ นับเป็น finding ห้ามรันซ้ำจนกว่าจะ green
- งาน UI ใช้ **browser** ทั้งจอ desktop และ mobile

เสร็จเมื่อ: ทุกแถวที่เลือกมีผล และ side channel ไม่มี error ใหม่

## 4. แก้ที่ root cause

1. reproduce ให้ red ได้ด้วยคำสั่งเดียว
2. ไล่จากอาการย้อนกลับไปหาจุดแรกที่ค่าผิด ถาม "ทำไม" ต่อจนเจอจุดที่แก้แล้วอาการนี้และอาการพี่น้องหายพร้อมกัน ถ้าข้ามหลาย component ให้ใส่ log ที่รอยต่อเพื่อหาว่าค่าผิดตั้งแต่ชั้นไหน
3. แก้ครั้งเดียวที่ต้นทาง แล้วเพิ่ม oracle ให้ caller ใน blast radius ที่ bug report ไม่ได้พูดถึง
4. คง **contract** เดิมของโค้ดที่ใช้ร่วมกัน คือรูปแบบของ interface (ชื่อ, parameter, ชนิดค่าที่คืน, คืนค่าหรือ throw, ค่า default) ส่วนค่าที่คำนวณผิด เช่น ยอดเงินคลาดจาก float ไม่ใช่ contract ให้แก้ให้ถูก ถ้าการแก้ที่ถูกต้องต้องเปลี่ยน contract ให้ไล่ทุก caller ว่ารับได้ เพิ่ม oracle ให้แต่ละตัว แล้วเขียนเป็นการตัดสินใจที่ผู้ใช้ต้องรู้ในรายงาน
5. green: รัน oracle ที่เคย red ทั้งหมด รัน test ที่เกี่ยวข้องระหว่างวนแก้ แล้วรัน test ทั้งชุดครั้งเดียวก่อนรายงาน (ถ้าเกินราว 10 นาที ให้รันชุดที่เกี่ยวข้องและระบุชุดที่ข้าม)
6. tier risky: **mutation check** วาง bug จงใจ 1-2 จุดในบรรทัดที่แก้ (กลับเงื่อนไข, ลบการปัดเศษ) ดูว่ามี oracle red แล้วเอาออก ถ้าไม่มีตัวไหน red ให้เพิ่ม oracle

ถ้าสมมติฐาน 2 ข้อแรกผิด ให้ขอ **ความเห็นที่สองเมื่อติด** แบบ read-only ก่อนลองข้อที่ 3 ถ้า 3 แนวทางยังไม่ผ่าน ให้หยุดแล้วรายงานสิ่งที่ลอง หลักฐาน และสาเหตุที่สงสัย

เสร็จเมื่อ: oracle ทุกตัว green, test ทั้งชุด green, และอธิบาย root cause ได้ในหนึ่งประโยคที่ชี้ `file:line`

## 5. ผู้ตรวจอิสระหนึ่งตัว (tier risky)

ใช้ **ผู้ตรวจอิสระ** ตัวเดียว ถ้ากฎของผู้ใช้สั่ง code review ภายนอกสำหรับงานนี้อยู่แล้ว (เช่น Codex review ใน CLAUDE.md) ให้ review นั้นเป็นผู้ตรวจของขั้นนี้ โดยใส่คำสั่งข้างล่างลงใน prompt ของมันด้วย ไม่ต้องส่งผู้ตรวจตัวที่สอง

ส่งให้ผู้ตรวจแค่ claim, วิธีรัน, และ diff (รวม diff ของไฟล์ test) สั่งให้หา input ที่ทำให้ claim เป็นเท็จ และตรวจว่า diff มีการแก้ test หรือ special-case input หรือไม่ ให้ผู้ตรวจคืนรายการ input ที่ลองพร้อมผลของแต่ละตัว ตรวจรายการนั้นกับ diff เองก่อนเชื่อ

finding ทุกข้อต้อง reproduce ให้ red ก่อนแก้ แล้ววนกลับขั้น 4

เสร็จเมื่อ: ผู้ตรวจคืนรายการ input ที่ลองแล้วไม่มีตัวไหนพัง หรือทุก finding ที่จริงถูกแก้และมี oracle กันไว้

## 6. รายงาน proof

ประโยคแรกตอบว่าพิสูจน์ได้หรือไม่ แล้วตามด้วยตาราง:

| claim | oracle | ก่อนแก้ | หลังแก้ | หลักฐาน |
|---|---|---|---|---|

- หลักฐานคือ path ของไฟล์ raw evidence, คำสั่งที่รันซ้ำได้ หรือ path ของ screenshot
- บอก tier, root cause, สิ่งที่แก้ (`file:line`) และเครื่องมือที่ใช้แทนตัวแรก
- แถวแยกสำหรับทุกการเปลี่ยน test และทุกการเปลี่ยน contract
- หัวข้อ **ยังไม่ได้พิสูจน์**: ทุก claim ที่ทดสอบไม่ได้ พร้อมเหตุผลและวิธีที่ผู้ใช้จะพิสูจน์เอง
- ใช้คำที่ตรงกับหลักฐาน: "ผ่าน" เมื่อมี output, "ยังไม่ได้ตรวจ" เมื่อไม่มี

**ไฟล์ PDF**: เขียนรายงานฉบับเต็มเป็น `proof-report-<YYYYMMDD-HHMM>.md` ใน **ที่เก็บหลักฐาน** (หัวเรื่อง `#` บรรทัดแรกบอกสิ่งที่พิสูจน์) screenshot ให้ฝังด้วย path relative จากที่เก็บหลักฐาน `![ก่อนแก้: หน้า checkout](before.png)` (path เต็มก็ได้ ถ้ามีช่องว่างให้ครอบด้วย `<...>`) แล้วแปลง: `bash "{path_to_skill}/../../scripts/to-pdf.sh" "<path ของ .md>"` (`{path_to_skill}` คือ directory ที่ SKILL.md นี้ถูกโหลดมา) script พิมพ์ path ของ PDF ออกมา ให้ `open` PDF และบอก path ของทั้ง .md และ .pdf ในคำตอบ ส่วนในแชทให้ตอบแค่ประโยคแรก ตาราง และหัวข้อ "ยังไม่ได้พิสูจน์" ถ้า script fail (ไม่มี Chrome หรือ npx) ให้ส่งแค่ .md พร้อมเหตุผล
